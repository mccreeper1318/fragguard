> **RELEASE GATE: NOT SIGNED OFF.** This document describes tests and operating checks; it does not authorize a release, live database migration, file replacement, or `dev` → `main` merge. Issue #172 and tracker #158 stay open until the owner reviews the live evidence.

## Test environments and limits

- All automated SQLite tests create **synthetic** databases in isolated temporary directories. They never open a server's live `plugins/FragGuard/fragguard.db`, `-wal`, or `-shm`.
- Standard CI runs `./gradlew --no-daemon --warning-mode all clean test build`. `MaintenanceReleaseValidationTest` seeds **3,000** rows plus real-shaped rollback job, undo BLOB and chunk reservation, checks the full compaction/verifier/STRICT/restart path, and refuses strict replacement after a post-snapshot write.
- Independently reviewed 26.3-1.2.2 issue suites also cover persistent state and crash recovery (`MaintenanceCoordinatorTest`), deadlines and Boss Bar (`MaintenanceNoticeDisplayTest`), OP/staff bypass and kick/login (`MaintenanceAdmissionGateTest`), admin command permissions (`MaintenanceCommandIntegrationTest`), quota and path races (`CompactionStoragePreflightTest`), cancelled/overlapping VACUUM and WAL writer continuity (`OnlineDatabaseCompactionTest`), BLOB/index/undo tampering (`CompactionCandidateVerifierTest`), strict/snapshot consent and late source changes (`CompactionReplacementPolicyTest`), and wrong sidecars/incomplete swaps/checkpoint failures/startup recovery (`CompactionActivationTest`).
- Prior tests include `LargeHistoryMigrationIntegrationTest`, `RetentionCleanupBatcherTest`, `DatabaseTest`, `DatabaseDeepDiagnosticsTest`, `MaintenanceRollbackGateTest`, and `ReclaimableSpaceMonitorTest`. **A passing CI suite does not establish live TPS, host quota, backup correctness, or 57-million-row performance.**

### Optional isolated scale test

On a **separately provisioned non-production runner** with disposable storage, a representative fixture can be generated and checked with:

```sh
FG_COMPACTION_VALIDATION_ROWS=200000 ./gradlew --no-daemon --rerun-tasks test --tests '*MaintenanceReleaseValidationTest'
```

Gradle declares `FG_COMPACTION_VALIDATION_ROWS` as a tracked test input, so changing the row count invalidates UP-TO-DATE/cached results. The documented `--rerun-tasks` also forces a fresh execution when repeating the **same** row count; verify the test log prints the requested `rows=` value rather than accepting a cached or skipped run.

For 57-million-row validation, set `FG_COMPACTION_VALIDATION_ROWS=57000000` **only** if the owner has confirmed ample extra disk space and native SQLite temp/quota headroom, RAM, and a long maintenance window on an isolated runner. Do not run this size in ordinary GitHub-hosted CI or against a real backup unless it was first copied, isolated and independently verified. The test runs a full scan more than once and may use very large temporary DB/WAL/candidate files. It prints row count, runtime, source-backup and candidate sizes, and actual snapshot time *bounds*; these are not guarantees of production run time or safe space. Do not claim that the 57M test passed until its full logs and checksums are recorded.

## Fault-injection/coverage matrix

| Scenario | Automated test evidence | Required release result |
| --- | --- | --- |
| Countdown, stalled tick, late joiner, yellow Boss Bar decrease, chat warnings | `MaintenanceCountdownClockTest`, `MaintenanceNoticeDisplayTest` | Correct remaining time, exactly-once expiry, no duplicated warnings |
| Regular player kick/rejoin, OP or bypass staff, permissions revoked mid-session | `MaintenanceAdmissionGateTest` | Regular players rejected; staff bypass authorized; restored access after cancellation |
| Admin-only GUI and commands, attempted bypass via permission alone | `MaintenanceCommandIntegrationTest`, `MaintenanceUiActionsTest`, `MaintenanceGuiInventoryLayoutTest` | No actions without OP + `fragguard.admin`; bypass permission is distinct |
| Cancellation / stale persisted stage / failed state write and restart | `MaintenanceCoordinatorTest`, `OnlineDatabaseCompactionTest` | Fail closed; no automatic promotion or deletion |
| Disk/account/temp quota shortage, unknown quota, stale preflight, collision/symlink | `CompactionStoragePreflightTest` | Refuse known shortage; unknown requires independent explicit acknowledgement |
| Partial candidate, cancelled VACUUM, mismatching copy / missing evidence | `OnlineDatabaseCompactionTest`, `CompactionCandidateVerifierTest` | Never produce a trusted manifest or replace original |
| Integrity, index, BLOB, world UUID, rollback/undo and chunk reservation | `DatabaseDeepDiagnosticsTest`, `CompactionCandidateVerifierTest`, `MaintenanceReleaseValidationTest` | All schema, indexes, rows and saved snapshots verified |
| Live writer continues while VACUUM copies a coherent snapshot | `OnlineDatabaseCompactionTest` | Source remains writable; candidate remains internally consistent |
| Post-copy changes, snapshot-loss consent and STRICT source refusal | `CompactionReplacementPolicyTest`, `MaintenanceReleaseValidationTest` | STRICT rejects any changed source; snapshot mode needs exact recorded consent |
| WAL checkpoint fails, wrong/missing DB/WAL/SHM, manual swap partially performed | `CompactionActivationTest` | No receipt/activation; originals preserved |
| Failed startup, corrupt manifest, interrupted ACTIVATING and retry | `CompactionActivationTest`, `MaintenanceCoordinatorTest` | Cannot clear maintenance or enter restart loop with untrusted state |
| Retention deletes, rollback/undo safety, logging continues after cleanup errors | `RetentionCleanupBatcherTest`, `DatabaseTest`, `MaintenanceRollbackGateTest` | No history/undo loss except the explicitly approved snapshot policy |
| Bounded memory and Paper main thread / tick responsiveness | Worker-thread isolation in compaction, verifier, read-only diagnostics, display and command tests | **Must also measure live TPS and memory on the Paper host** |

**Important limitations:** Automated tests cannot reproduce every disk-full/quotas or OS failure, nor prove the actual server's TPS or that a host file manager implements atomic moves. Where faults are simulated, the expected behavior is refusal without deleting the original or overwriting unknown files.
